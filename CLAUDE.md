# Mbokk — Digital Family Register (Senegal)
## Status

Phases 0–4 complete: scaffolding, DB schema/models/seeder, phone auth (invite links + PIN — Phase 2 revised 2026-07-24 to drop OTP/SMS entirely, see `docs/mvp-plan.md`), family-tree/people CRUD, and relationships/cross-family linking. Backend controllers use dedicated `FormRequest`/API `Resource`/`Policy` classes throughout, not inline validation. Every endpoint — success or error, thrown or manual — responds through one envelope via `ApiResponse`. `Person::wouldCreateCycle()` is now actually enforced (`StoreRelationshipRequest`), and cross-tree linking is verified working.

Phase 5 (`docs/mvp-plan.md:67`) is complete, backend and frontend — contributor writes now go through `edit_proposals` instead of a 403: `PersonController`/`RelationshipController` branch on `Gate::denies('create'|'update'|'delete', ...)`, falling back to `PersonPolicy::proposeCreate()`/`proposeOnPerson()` (any tree member) to create an `EditProposal` instead. `TreeMemberController` handles phone-based invites; `EditProposalController` handles the admin/owner approve|reject queue, replaying the stored payload through the same `Person`/`Relationship` models a direct write would use. `GET /trees/{slug}` now also returns the caller's `role`, which the frontend uses to gate the new `TreeMembers`/`EditProposalsQueue` components (owner/admin only); `PersonForm`/`PersonRelationships` mutations detect a 202 `EditProposal` response via `isEditProposal()` and show a pending-approval message instead of assuming the write applied.

Phase 6 (`docs/mvp-plan.md:74`) is complete — `SearchController` (`GET /search`, unauthenticated, public people/trees only) is distinct from Phase 4's auth-scoped `PersonSearchController`; `RelationshipFinderController` (`GET /people/{id}/relationship/{otherId}`) BFS-walks `relationships` as an undirected graph, gated by `PersonPolicy::view()` on both people. Frontend: `Nav` (global header, search bar — first real consumer of the `Nav.*` next-intl strings, mounted in `layout.tsx`), `/search` (SSR results page), `/relationship-finder` (authed, two person-pickers + path rendering). Both search controllers use `whereLike()`/`orWhereLike()`, not raw `ilike` — `ilike` is Postgres-only and breaks on the sqlite test DB (`phpunit.xml`); `whereLike()` compiles correctly on both. Don't reintroduce raw `ilike` in new search code.

Phase 7 (`docs/mvp-plan.md:79`) is complete — `FamilyTreeView` ports `mbacke-genealogy-app.tsx`'s tree visualization as a generalized, data-driven `/web` component: generation depth is computed via Kahn's algorithm over `parent_of` edges (correctly handles multi-parent people, unlike the reference file's static `generation` field), fed by `relationships` now included in `GET /trees/{slug}`'s response (only edges between two people already in that response — cross-tree links aren't laid out in the SVG). `PersonProfileController` (`GET /people/{id}`, public, numeric-constrained) serves the SSR `/people/[id]` profile page, only for `is_public` people, filtering relationships to public counterparts. `mbacke-genealogy-app.tsx` itself is untouched (Architecture Laws) — it remains scaffolding input, not a file to extend.

## Project Structure

- `api/` — Laravel 13 backend. Sanctum installed via `install:api`; `routes/api.php` is the real routes file (not `routes/web.php`).
  - `app/Models/` — `User` (phone + `pin_hash`, `HasApiTokens`), `FamilyTree`, `TreeMember`, `Person`, `Relationship`, `EditProposal`, `InviteToken` (single-use, expiring — how everyone but a first-tree bootstrapper logs in), `AccessRequest` (the self-serve "I lost access" ask — resolving one still means an admin re-invites the phone number, it doesn't grant access by itself). `Person::children()`/`parents()` are real `BelongsToMany` through the `relationships` pivot; `Person::spouses()` is a plain method (not a relation) merging both pivot directions since `spouse_of` has no canonical side. `Person::wouldCreateCycle($parentId, $childId)` is called from `StoreRelationshipRequest` before any `parent_of` insert — verified against real cross-tree data.
  - `app/Http/Controllers/` — `Auth/AuthController` (`register`, bootstrap-only account creation, trust-on-first-use; `login`, returning-user recovery by phone + PIN, added 2026-07-30 — refuses accounts with no `pin_hash` yet rather than trust-on-first-use setting one, since an existing account already has a real owner and letting anyone who knows the phone number set the PIN first would be account takeover, not just claiming an unclaimed number; `setPin`, `auth:sanctum`-gated, lets an already-authenticated user set their PIN proactively — also 2026-07-30, also refuses if `pin_hash` is already set, one-shot only, no "change PIN" flow yet), `InviteController` (`claim` — claiming a link is how everyone else logs in, no code involved), `FamilyTreeController` (`show()` also returns `relationships` — only edges between two people already in the `people` payload, for `FamilyTreeView` — plus the caller's `role`; still returns every person unpaginated, needed for the SVG tree layout), `PersonController` (`index`, added 2026-08-10 — paginated, fixed `PER_PAGE = 30` not client-controlled, ordered alphabetically by first/last name, manually building `meta` alongside the `PersonResource` collection since `ApiResponse::success()` wraps the payload itself rather than returning a resource collection directly, which is what triggers Laravel's automatic pagination-metadata injection; what `/trees/[slug]`'s "Liste" tab actually renders from, so a tree with thousands of people doesn't mean thousands of DOM rows — the "Arbre" SVG tab still needs the full unpaginated set from `FamilyTreeController::show()` to lay out the diagram at all, pagination doesn't help that one), `RelationshipController` (`index`/`store`/`destroy`, cross-tree by design), `PersonSearchController` (single-action, cross-tree person search for the "link to existing person" UI — `is_public` or own-tree scoped, distinct from `SearchController` below; optional `tree` query param, added 2026-08-10, narrows results to one slug — still only within the already-allowed scope, a strict subset, not a bypass; used by `PersonRelationships`' "uniquement dans cette famille" checkbox), `TreeMemberController` (`index`/`store` — invite by phone, `store()` issues a fresh single-use `InviteToken` every call, including re-inviting an existing member, which also auto-resolves any matching pending `AccessRequest`), `AccessRequestController` (`store` public/unauthenticated — the point is reaching someone with no session; `index`/`dismiss` owner/admin only, same `manageMembers` gate as `TreeMemberController`), `EditProposalController` (`index`/`approve`/`reject` — the latter two require a `pin` field, checked by the private `checkPin()` helper, not a `FormRequest`, since it's one field shared by both actions), `SearchController` (single-action, public/unauthenticated directory search — `GET /search`, outside the `auth:sanctum` group, public people + trees only), `RelationshipFinderController` (single-action, `GET /people/{id}/relationship/{other}`, BFS over `relationships` as an undirected graph, gated by `PersonPolicy::view()` on both people), `PersonProfileController` (single-action, `GET /people/{id}`, public/unauthenticated, numeric route constraint so it never shadows `/people/search`; only serves `is_public` people, filters relationships to public counterparts). All take `FormRequest` subclasses (except the plain `Request`-typed single-action controllers, gated via `Gate::authorize`/policy calls directly) and return API `Resource` classes — never inline `$request->validate()` or bare models in a JSON response; follow this pattern for new endpoints too.
  - `app/Http/Requests/` — one per write endpoint. `authorize()` on the Person/Relationship requests checks *both* the owner/admin ability (`create`/`update`) *and* the any-member propose ability (`proposeCreate`/`proposeOnPerson`) via `$this->user()->can(...)` — the controller then branches on `Gate::denies('create'|'update'|'delete', ...)` to decide whether to write directly or create an `EditProposal`. `StoreRelationshipRequest::withValidator()` is where cycle-prevention and duplicate-relationship checks live (not the controller), and it runs regardless of which path (direct write or proposal) the request ends up taking.
  - `app/Policies/PersonPolicy.php` — `view()` (public, or tree member) gates reads; `create`/`update`/`delete` are owner/admin only. `proposeCreate()`/`proposeOnPerson()` are any-tree-member (including contributors) — that's the ability contributors actually pass, which is what routes their write into `edit_proposals` instead of a 403. Adding a relationship reuses `update`/`proposeOnPerson` on the *acting* (route) person — the target person's tree isn't checked, that's the whole point of cross-family links.
  - `app/Policies/FamilyTreePolicy.php` — `manageMembers()` (owner/admin only) gates inviting members and viewing/reviewing the proposals queue.
  - `app/Policies/EditProposalPolicy.php` — `review()` (owner/admin of the proposal's tree) gates approve/reject.
  - `app/Http/Resources/` — `UserResource`, `FamilyTreeResource`, `PersonResource`, `RelationshipResource`, `TreeMemberResource`, `EditProposalResource`. `PersonResource` computes `photo_url` from `photo_path` via `Storage::disk('public')->url()` — never expose `photo_path` directly to the frontend. It also has an optional `family_tree` field (`whenLoaded('owningFamilyTree')`) used only by search results, to disambiguate same-name people across trees. `EditProposalResource` flattens `payload` into `action`/`fields` for the frontend rather than exposing the raw JSON column.
  - `app/Http/Responses/ApiResponse.php` — `ApiResponse::success($data, $message, $status)` / `::error($message, $status, $errors)`. Every controller returns through this — never `response()->json()` directly. `success()` with `status: 204` returns a real empty body, not `{"data": null}`. Also has `authorizationMessage()` — see the `bootstrap/app.php` note below.
  - `bootstrap/app.php` — `withExceptions()` renders `ValidationException`/`AuthenticationException`/`ModelNotFoundException`/`NotFoundHttpException` through `ApiResponse::error()`. For 403s it renders `AccessDeniedHttpException`, **not** `AuthorizationException` — Laravel's `Handler::prepareException()` converts the latter to the former internally *before* `render()` callbacks run, so a naive `AuthorizationException` handler silently never fires (learned this the hard way — verify with a real curl 403, don't trust that the handler "should" work). Add new exception types here, not per-controller try/catch.
  - `lang/fr/validation.php` — French validation messages + `attributes` translations (phone → téléphone, etc.). Required because `APP_LOCALE=fr` — without this file Laravel falls back to raw untranslated keys like `"validation.required"`.
  - `database/seeders/FamilyTreeSeeder.php` — the only seeder. Rewritten 2026-07-30 to seed the real Mbacké ascendance (both branches up to the shared ancestor Mame Mahram Mbacké) plus Cheikh Ahmadou Bamba's sons as reported to the project, replacing the earlier `mbacke-genealogy-app.tsx`-derived placeholder khalife data. ## Architecture Laws

- NEVER build real-time collaborative editing — model is async propose/approve only (contributors propose, tree admin/owner approves).
- ALWAYS make privacy per-person, not per-tree — `people.is_public` defaults true, opt-out per individual.
- ALWAYS allow relationships to reference people owned by a *different* family tree — this is how cross-family links work; do not add a separate "link" table for this.
- NEVER let a person become their own ancestor — `StoreRelationshipRequest::withValidator()` calls `Person::wouldCreateCycle($parentId, $childId)` before any `parent_of` insert. Don't add a new relationship-writing path without the same check.
- Contributor writes ALWAYS go through `edit_proposals`; only owner/admin write directly to `people`/`relationships` — enforced via `PersonPolicy`. Adding a relationship checks the *acting* person's tree only, never the target's — that's what makes cross-family linking possible without needing rights on the other family's tree.
- Backend controllers ALWAYS use dedicated `FormRequest` + API `Resource` classes — no inline `$request->validate()`, no bare Eloquent models in a JSON response (see `app/Http/Controllers/`).
- Every API response ALWAYS goes through `ApiResponse::success()`/`::error()` (`app/Http/Responses/ApiResponse.php`) — never `response()->json()` directly in a controller. New exception types that should render as JSON errors get a handler in `bootstrap/app.php`, not a per-controller try/catch.
- Auth is phone-based ONLY — no email/password flow. The app NEVER sends SMS/WhatsApp/any message: joining an existing tree happens by claiming an admin-shared invite link (`InviteToken`, single-use, expiring), not a sent code; the only self-serve path is bootstrapping a brand-new first tree (`POST /auth/register`), which is trust-on-first-use and explicitly refuses to work on an already-registered phone number (that would make it an account-takeover backdoor around the invite-link model). `users.name` is nullable because the row can be created before a name exists (at invite time, or at bootstrap if left blank). A returning user with an already-registered phone recovers a session via `POST /auth/login` (phone + PIN, added 2026-07-30 to close the dead end where a sole tree owner who lost their token had no other admin to re-invite them) — but this is *not* self-serve login recovery in the OTP/password-reset sense: it only works once `pin_hash` is already set, and there is still no way to set or reset a PIN from an unauthenticated state. `AccessRequestController` remains the fallback for accounts with no PIN yet — it only makes the ask for a fresh invite, resolving one always still means a real admin action.
- A PIN (`users.pin_hash`) gates `EditProposalController::approve`/`reject` (where it's still trust-on-first-use set) **and**, as of 2026-07-30, `AuthController::login` (session recovery) — never an app-open lock, and `login` never sets a PIN itself, only checks one that already exists. Extending PIN usage further needs the same reasoning re-applied: is trust-on-first-use safe here, or does the target account already have a real owner who'd be taken over?
- Public person/search pages must be SSR/SSG (SEO-driven); authenticated tree-editing views are client-fetched (TanStack Query) — don't invert this.
- Do not architect for national scale — this is explicitly a small/personal-project-scale system for now.
- UI components are shadcn/ui (`base` library + Tailwind, copy-in) — do not pull in a separate styled component library (Mantine/Chakra/MUI) alongside it, and do not restore shadcn's default theme (see `web/src/app/globals.css`).

## Coding Conventions

- New backend code goes under `/api` (Laravel), new frontend under `/web` (Next.js) — do not create either at repo root.
- Relationship rows use `type: parent_of | spouse_of`; spouse rows support polygamy (multiple `spouse_of` rows per person) — never model marriage as a single nullable spouse field.
- French-only user-facing strings for MVP, routed through `next-intl` scaffolding even though only one locale ships — don't hardcode strings that bypass i18n.

## Anti-patterns

- ❌ Real-time sync (websockets/CRDTs for tree editing) → ✅ async edit_proposals + approval
- ❌ Separate `family_links` table for cross-tree connections → ✅ `relationships` rows referencing people in another tree directly
- ❌ Single spouse field on `people` → ✅ multiple `spouse_of` relationship rows (polygamy support)
- ❌ Blocking/hardcoded English or French-only strings outside next-intl → ✅ scaffold via next-intl now, even for French-only MVP content
- ❌ Extending `mbacke-genealogy-app.tsx` in place → ✅ port its logic into `/web` as a generalized, data-driven component (Phase 7)
- ❌ Inline `$request->validate()` / returning raw models from a controller → ✅ `FormRequest` + API `Resource` (`app/Http/Requests/`, `app/Http/Resources/`)
- ❌ Ad-hoc role checks scattered in controllers → ✅ a `Policy` (see `PersonPolicy`), invoked from the `FormRequest::authorize()` or via `Gate::authorize()`
- ❌ `response()->json([...])` built ad-hoc per controller → ✅ `ApiResponse::success()`/`::error()` — one envelope shape everywhere
- ❌ Checking the *target* person's tree when adding a relationship → ✅ only check the acting (route) person's tree — the target may legitimately belong to another family
- ❌ A `render()` handler for `AuthorizationException` alone → ✅ handle `AccessDeniedHttpException` too (Laravel converts the former to the latter before dispatch)

## Key Files

- `docs/mvp-plan.md` — canonical source of decisions, data model, and phase checklist; consult before making any architectural choice.
- `api/routes/api.php` — all backend routes live here, not `routes/web.php`.
- `api/config/cors.php` — origin allowlist, driven by `FRONTEND_URL`. Also read via `config('app.frontend_url')` (`api/config/app.php`) to build shareable invite links in `TreeMemberController@store` — same env var, two consumers.
- `api/app/Models/User.php` — has `HasApiTokens`; this is where Sanctum token issuance hangs off.
- `api/app/Models/Person.php` — `wouldCreateCycle()` cycle guard and the `children()`/`parents()`/`spouses()` relations; consult before touching relationship-writing code.
- `api/app/Policies/PersonPolicy.php` — the owner/admin write check + `view()` privacy gate, plus the `proposeCreate()`/`proposeOnPerson()` any-member abilities that route contributor writes into `edit_proposals`; every future Person/Relationship endpoint should reuse or mirror this.
- `api/app/Http/Requests/StoreRelationshipRequest.php` — cycle + duplicate validation; the reference implementation for any future relationship-writing endpoint.
- `api/app/Http/Controllers/EditProposalController.php` — `applyProposal()` is where an approved proposal's stored `payload` gets replayed into a real `Person`/`Relationship` write; the reference for adding a new proposable action.
- `web/next.config.ts` — wires the next-intl and Serwist build plugins (Serwist disabled outside `NODE_ENV=production` — Turbopack dev doesn't support it); both wrap the config object, order matters if a third plugin is added.
- `web/components.json` — shadcn/ui config (`base` library, not Radix).

## Environment
